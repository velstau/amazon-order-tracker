# 引継書：Amazon 注文履歴トラッカー（Chrome 拡張）

作成日：2026-10-01
状態：**初版完成（2026-10-01、実機で全期間同期・表示ともにユーザー確認済み）**

---

## 1. 目的

Amazon での支出を把握するための画面を作る。Amazon 自体にこの機能がないため自作する。

見たいもの：

- **今月いくら使ったか**（月別の合計）
- **いつ・何を買ったか**（注文日・商品名・金額）
- **いつ届いたか**（配達日・配達状況）

対象は **amazon.co.jp**（個人アカウント）。

---

## 2. 決定事項：Chrome 拡張で作る（Laravel ではない）

決め手は **データの取得方法**。Amazon には個人の注文履歴を取れる公開 API がない。

| 案 | 判断 | 理由 |
|---|---|---|
| **Chrome 拡張** | **採用** | ログイン済みブラウザのセッションで注文履歴ページを取得できる。認証の処理が不要 |
| Laravel でサーバーから取得 | 不採用 | サーバーからのログインは 2 段階認証・CAPTCHA・ボット検知に阻まれる。アカウントロックの恐れもある |
| Laravel ＋「データのリクエスト」CSV | 不採用 | 正確だが、申請から届くまで数日かかる手動運用になる |
| Laravel ＋ Gmail の注文メール解析 | 不採用 | 商品名の省略、分割発送、キャンセル・返品の反映漏れがある。メールの書式が変わると壊れる |

**将来の拡張**：長期保存や Laravel 側の画面が欲しくなったら、拡張で集めたデータを PHP（Laravel）側の API に POST する構成を後から足す。**最初は拡張だけで完結させる。**

---

## 3. スコープ（初版）

### やること

1. ツールバーのアイコン（またはダッシュボード上のボタン）から「履歴を同期」を実行する
2. amazon.co.jp の注文履歴を年単位・ページ単位で取得し、HTML を解析する
3. 取得結果を拡張内に保存する（IndexedDB を推奨。件数が増えるため `chrome.storage.local` より向く）
4. ダッシュボード（拡張内の HTML ページ、新しいタブで開く）で表示する
   - 今月の支出合計（大きく表示）
   - 月別合計（直近 12 か月程度の棒グラフか表）
   - 注文一覧：注文日／商品名／金額／配達状況・配達日／注文詳細へのリンク
   - 絞り込み：月、キーワード、未配達のみ
   - 未配達（配送中・発送準備中）の一覧

### やらないこと（初版）

- Laravel 連携
- amazon.co.jp 以外のドメイン、ビジネスアカウント
- 定期的な自動同期（まず手動同期で安定させる）→ 2026-10-01 に「ダッシュボードを開いたときの自動同期」だけ追加した（下記）
- 返品・返金額の正確な反映（「返品済み」などのステータス表示にとどめる）

## 4. 取得項目とデータモデル（案）

注文単位で 1 レコードとし、商品は配列で持つ。

```js
// orders ストア（keyPath: orderId）
{
  orderId: "250-1234567-1234567",
  orderDate: "2026-09-20",          // ISO 形式に正規化する
  total: 3280,                      // 注文合計（円・整数）。キャンセル済みの注文では表示されず null
  status: "delivered",              // delivered / pending / cancelled / returned / unknown
  statusText: "9月25日にお届け済み", // 画面表示の原文（分割発送は " / " 区切り）
  deliveredDate: "2026-09-25",      // delivered のとき。発送が複数なら最も遅い日
  expectedDate: null,               // pending のときの配達予定日。曜日だけの表示は取得日から求める
  items: [
    { title: "商品名", asin: "B0XXXXXXX", url: "https://www.amazon.co.jp/dp/B0XXXXXXX", imageUrl: "..." }
  ],
  shipments: [                      // 配送ボックス（発送）単位
    { statusText: "9月25日にお届け済み", detailText: "ご注文商品を郵便受けに配達しました。", status: "delivered", date: "2026-09-25", items: [...] }
  ],
  detailUrl: "https://www.amazon.co.jp/your-orders/order-details?orderID=...",
  fetchedAt: "2026-10-01T12:00:00+09:00"
}
```

- 1 注文に複数の発送（分割配送）がある場合、配達状況が発送ごとに異なる。注文単位の代表ステータスは、未配達が 1 つでもあれば pending、キャンセル以外がすべて配達済みなら delivered とする。一覧ページに発送単位の情報があったので、`shipments` にも保持する
- **`shipping` と `preparing` は分けない（2026-10-01 変更）**。一覧ページでは「10月15日にお届け」のような予定日しか出ず、発送前か配送中かを区別できないため、未配達はまとめて `pending` とする
- 再同期では `orderId` で上書き（upsert）する。配送中だった注文のステータスが更新されるようにするため。

## 5. 「支出額」の定義（初版の仕様）

「支出額」には複数の解釈があるので、初版はこう決める。

- **集計対象：注文合計（total）**
- **除外：キャンセル済みの注文**
- **月の帰属：注文日の月**

ほかの解釈は把握したうえで、初版では扱わない。

- 実際の請求額：分割発送では発送ごとに請求される
- ポイント・ギフト券を差し引いた実支払額：領収書ページで確認できる可能性がある（要確認）

## 6. 技術方針

- **Manifest V3、素の JS / HTML / CSS、ビルドなし。** 姉妹の拡張（SmartGain）と同じ流儀にする
- 権限は最小限にする：`storage`、host_permissions は `https://www.amazon.co.jp/*` のみ
- **HTML の解析場所に注意：** Service Worker では `DOMParser` が使えない。解析は **ダッシュボードページ（拡張ページ）** か **amazon.co.jp 上のコンテンツスクリプト** で行う
- 取得方式は次の順で試す
  1. **拡張ページから `fetch(url, { credentials: "include" })`**：host_permissions があれば Cookie 付きで取得できる想定。ただし SameSite Cookie の扱いで失敗する可能性がある（**要検証**）
  2. 1 が駄目なら **amazon.co.jp のタブで動くコンテンツスクリプトから同一オリジンで fetch** し、結果をメッセージで拡張側に渡す
- **パーサーは 1 ファイル（例：`parser.js`）に集約する。** Amazon はページ構造をよく変えるため、壊れたときに直す箇所を 1 か所にしておく。セレクタは定数としてファイル冒頭にまとめる
- **アクセス間隔：** ページ取得の間に 1〜2 秒程度の待機を入れる。規約上グレーな行為なので、負荷をかけないことを優先する
- UI の文字サイズは **最低 1.0rem**（ユーザーの必須要望）

## 8. 次の一手（推奨の進め方）

1. ユーザーから注文履歴ページの HTML（直近分 1〜2 ページ）を受け取る。**そこから DOM 構造とセレクタを確定する**
2. `manifest.json` と、拡張ページから 1 ページだけ fetch して件数をコンソールに出す最小の試作を作る。**Cookie 付き fetch が通るかをここで判定する**（通らなければ 6 章の方式 2 に切り替える）
   - 2026-10-01 作成済み：`dashboard.html` で方式 1・方式 2 を、新旧 2 形式の URL それぞれについて判定できる。方式 2 のために `scripting` 権限を追加した（方式 1 が通れば外す）
   - **判定結果（2026-10-01）：全 4 件成功。方式 1 を採用する。** `scripting` 権限と方式 2 のコードは同期処理の実装時に削除する。URL は新形式（`/your-orders/orders`）を採用する
   - 取得した HTML は画面の「HTML を保存」で保存できる。手順 1 の HTML はこれで代用できる（ブラウザの「名前を付けて保存」は JS で書き換わった後の DOM になるが、こちらは fetch で実際に受け取る HTML と同じものになる）
3. `parser.js` を書き、受け取った HTML で解析結果を確認する（注文番号・日付・金額・ステータスが全件取れるか）
   - 2026-10-01 完了：`samples/` の 2 ページ 20 件をすべて解析できた（分割発送、3 点以上のカルーセル表示、キャンセル、￥0 の注文を含む）。検証は `tests/test_parser.js`（Node + jsdom、velworks-node コンテナで実行）
   - 暗号化された通常版のページを渡すと `encrypted: true` を返して解析しない。同期処理ではこれを異常として扱う
4. 年一覧とページ送りを含む同期処理、IndexedDB への保存
   - 2026-10-01 実装：`sync.js`・`db.js`。同期は 2 種類
     - **全期間**：1 ページ目の年一覧（`select#time-filter`）にある全年を読む。初回用
     - **最新分**：今年の新しい順に読み、「DB と同じ内容で確定済み（配達済み・キャンセル・返品）の注文だけのページ」かつ「DB 内で最も古い未配達の注文より古いページ」に達したら止める。未配達の注文が前年にあれば前年も読む
   - ページごとに保存するので、途中で中止・失敗しても取得済みの分は残る。ログイン切れ・CAPTCHA・暗号化ページ・HTTP エラーでは止めて画面に理由を出す
   - 方式 2 用の `scripting` 権限は削除した（権限は `storage` と amazon.co.jp のみ）
5. ダッシュボード：今月合計 → 月別合計 → 一覧・絞り込み → 未配達一覧の順に作る
   - 2026-10-01 実装：今月・先月の支出、直近 12 か月の棒グラフ（押すとその月で絞り込み、表でも見られる）、未配達一覧、注文一覧（月・キーワード・未配達のみ）
   - グラフは SVG ではなく HTML/CSS で描く。SVG の viewBox で縮小されると文字が 1rem 未満になるため。ダークモードは OS の設定に従う
   - `tests/test_dashboard.js`：fetch を差し替えて samples/ の HTML を返し、全期間同期（22 リクエスト）、最新分同期（2 ページで停止）、月別合計、絞り込み、エラー表示を検証（Node + jsdom + fake-indexeddb）。**実ブラウザでの見た目は未確認**
6. 実データで今月の合計を Amazon の画面と突き合わせて検証する
   - 2026-10-01：実機で全期間同期とダッシュボード表示が動くことをユーザーが確認した

### 初版の後に残っていること（必要になったら）

- 「返品」「今日」「明日」の配達表示と、最終ページのページ送りは実物で未確認（推測で対応済み）。解析できない注文があると画面上部に件数が出る
- 2025 年以前の古い注文に、別の書式がないか（解析エラーの件数で気づける）
- アイコン画像（`icons/`）が未作成で、ツールバーは標準アイコンのまま
- 3 章の「やらないこと」（Laravel 連携、返金額の反映など）

### 自動同期（2026-10-01 追加）

- **ダッシュボードを開いたとき・そのタブに戻ったとき**に、前回の同期の試行から 1 時間（`AUTO_SYNC_INTERVAL_MS`）以上たっていれば「最新分を同期」を実行する。データが空のとき（初回）は実行しない
- 間隔は成功ではなく試行の時刻（meta の `lastSyncAttempt`）で数える。CAPTCHA やログイン切れで失敗したときに、開くたびに再試行しないため
- **裏で定期的に動かす方式（chrome.alarms ＋ オフスクリーンドキュメント）は検討したうえで不採用。** ユーザーは「開いたときに最新なら十分、開かずに知る必要はない」とした。裏で動かすと、ログイン切れに気づけない・定期アクセスでボット判定されやすい・権限が増えるという欠点がある。必要になったら、`sync.js` などを `DOM_PARSER` 理由のオフスクリーンドキュメントで読み込めば流用できる（オフスクリーンからの Cookie 付き fetch は未検証）
